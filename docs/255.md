## 1. THE HEADLINE — AND IT IS A CORRECTION TO MY OWN `254` §3.1

`254` §3.1 described `mattymattmattmatt/007-VR` as *"`vr/src/gevr_gl.c`, 591 lines
of stereo GL on our decomp — **unrun**"*. That undersold the problem. It is not
unrun. **It is unreachable.**

`vr/shim/gevr_shim.h` documents the required call order for one VR frame:

```
gevr_shim_frame_begin()      once, before the game ticks
gevr_shim_get_pads()         after joyConsumeSamplesWrapper()
... the game ticks as normal ...
for each eye:
    gevr_shim_begin_eye(e)
    ... the game renders its display list ...
    gevr_shim_end_eye(e)
gevr_shim_frame_end()
```

**Grepping that tree for every one of those symbols outside `vr/` returns two
call sites in the entire repository:**

| Symbol | Call sites outside `vr/` |
|---|---|
| `gevr_shim_get_pads` | `src/joy.c:436` |
| `gevr_shim_eye_projection_n64` | `src/fr.c:719` |
| `gevr_shim_init` | **none** |
| `gevr_shim_frame_begin` / `frame_end` | **none** |
| `gevr_shim_begin_eye` / `end_eye` | **none** |
| `gevr_shim_eye_view_n64` | **none** |

Three things follow, and each is worth more than the 4,450 lines it took to find
them:

1. **`gevr_shim_init` is never called, so `g_vr.active` is never set.** Every
   accessor in `gevr_shim.c` opens with `if (!g_vr.active ... ) return 0;`. The
   one live call site, `fr.c:719`, therefore returns 0 on every frame and writes
   nothing. **The VR layer in that tree is dead code from the game's side.**
2. **There is no eye loop.** Nothing calls `begin_eye`, so the game's display
   list is still built and executed once per frame. There is no second pass to
   put a second projection into.
3. **`gevr_shim_eye_view_n64` has no call site at all.** Even if the rest were
   wired, the *projection* would be per-eye and the *view* would not — and the
   eye **translation** lives in the view matrix. An asymmetric frustum alone
   shifts the frustum; it does not separate the eyes.

**Point 3 is the important one, because it is `B1` again, from a completely
different codebase.** The recomp spent from `43` to `71` on "both eyes carry the
same image, 0 px disparity". A build wired the way 007-VR is half-wired would
produce exactly that, and for a reason visible from a grep rather than from a
RenderDoc capture. **Read the call sites before believing a reference tree
works.** That is `58`'s lesson, third repository.

### What 007-VR is still worth

It is worth a great deal, just not as running code:

- **It names the seam.** `fr.c`'s `viSetupCurrentPlayerView` builds
  `g_viProjectionMatrixF` with `guPerspectiveF` and immediately loads it as
  `G_MTX_PROJECTION`. That is where a per-eye frustum has to go on the game
  side, and **our `fr.c:696` is the same function** (ours already carries a
  `GE_PORT_NATIVE` block there for `gePortFovScale()`).
- **It gets the matrix convention right and says why.** `guPerspectiveF` and
  `guLookAtF` build **row-vector** matrices (`v * M`); OpenXR/GL work in
  **column-vector** (`M * v`). `transpose_to_n64()` in `gevr_shim.c:288` does the
  transpose explicitly, and the header states that writing a GL-convention matrix
  straight into an `f32[4][4]` bound for `guMtxF2L` renders a scrambled frustum.
  **That is a bug we now do not have to find.**
- **It states the yaw sign, from the decomp.** `gevr_engine.h`: `bondview2.c`
  builds the view rotation as a rotation about Y of `(360 - vv_theta)` degrees,
  so engine yaw grows **clockwise** from above and is the **negative** of the
  usual right-handed convention. Pitch it explicitly refuses to assert
  (`GEVR_ENGINE_PITCH_SIGN` is a constant with a calibration tool pointed at it)
  — which is the honest answer and we should copy the honesty, not guess.
- **`guPerspective` cannot express an off-centre frustum.** A headset frustum is
  asymmetric. The projection must be **replaced**, not adjusted. Also: leave
  `g_viPerspNorm` alone — it drives the RSP's perspective correction, which a PC
  backend does not use.

**None of that is a line of code we can copy. All of it is a day we do not lose.**

| Game-side projection build | `vendor/ge-decomp/src/fr.c:696` `viSetupCurrentPlayerView`, already carrying a `GE_PORT_NATIVE` block |

**Phase 1 starts from zero VR code in the native tree.** That is not a setback;
it means there is no half-wired layer to be misled by — which, per §1, is exactly
what the one available reference tree is.

### The trap that must be written down before any code

**`getv/port/fast3d/gfx_pc.c` is gitignored** (`233` §6.1). Every line of stereo
work in that file reaches the repository only through
`tools/fetch-thirdparty.sh regen`. **A fresh clone loses it otherwise.** If
Phase 1 touches `gfx_pc.c`, `regen` is part of the commit, not an afterthought.

### The second trap, read from source today

`gfx_run()` (`gfx_pc.c:5817`) is not a re-entrant draw call. It calls
`gfx_wapi->start_frame()` at the top and **`gfx_wapi->swap_buffers_begin()` at
the bottom**. Calling it twice per frame swaps twice. **Any design that replays
the display list per eye must split `gfx_run` or the present will fight it.**
This is not a hypothesis; it is six lines of that function.

## 3. THE TWO CANDIDATE ARCHITECTURES

They are genuinely different and the choice should be made on measurement, not
preference.

### A — game-side re-render (007-VR's shape)

The game builds and submits its display list **twice**, once per eye, with
`fr.c` writing a different projection and view each time.

- **For:** the reference tree already documents this shape; the projection hook
  is one line in a function we already modify; no `gfx_pc.c` change, so no regen
  gate.
- **Against:** doubles all game-side render work, and — the real unknown —
  requires `fr.c`'s per-frame state (`g_ViBackIndex`, `dynAllocateMatrix`, the
  DL arena) to survive being driven twice in one frame. **That is not
  established and must not be assumed.**

### B — renderer-side replay (the recomp's shape)

The game builds the display list **once**. `port_render.c` runs it twice, and
`gfx_pc.c` substitutes a per-eye matrix at `gfx_sp_matrix`'s `G_MTX_PROJECTION`
branch.

- **For:** one clean interception point already identified; the game side is
  untouched; game logic runs once, so no double-tick risk.
- **Against:** requires splitting `gfx_run` (§2's second trap), and every line
  is in the gitignored file.

**No recommendation is made here.** The deciding measurement is cheap and comes
first — see §4 step 1.

### What the recomp era does and does not carry over

`64`, `65`, `67`, `70`, `71` measured **working stereo at 90 Hz**
(`eye0=91 eye1=91`, `stereo=90 | OK`). **That was RT64 and Vulkan/D3D12
descriptor sets. None of that code applies to a Fast3D/OpenGL port.** What
carries is the *method*, and it is the most valuable thing in the corpus:

- **`70`'s gate shape.** A `PREDICTION:` line that computes the expected pixel
  disparity **before anyone looks at the screen**, followed by `REQUIRED:` and
  `TODAY:`. Then the question that makes it a gate rather than a smoke test:
  *"what would a working build have to do differently to fail this?"*
- **`65`'s harness.** Split the side-by-side window at the seam,
  cross-correlate the halves, report `dx` and `mean|L-R|`. A number, not an
  impression.
- **`67`/`70`'s failure mode.** Twelve hypotheses were falsified by argument
  before the real cause — two draws sharing one descriptor slot — was found by
  looking at what the GPU actually read. **Every correct-looking upstream stage
  is compatible with identical output.**
- **`49`'s instrument warning, which cost the most.** Two instruments in that
  tree **could not fail** — they compared things that always differ. Before
  trusting any Phase 1 instrument: **what would it print on a working build?**
  If the answer is "the same thing", it is not an instrument.

## 4. THE GATE, AND IT DOES NOT NEED A HEADSET

This is the part that changes the plan. **Phase 1's gate should be a desktop
side-by-side window with a numeric disparity readout, with no OpenXR in the
build at all.**

Reasons, all of them load-bearing:

- It decouples stereo from headset availability, runtime bringup, session
  lifecycle and the compositor — **four sources of failure that the recomp
  spent days untangling from the one question actually being asked.**
- It is measurable from a screenshot by a script, so it does not depend on a
  worn report. `254` §1's lesson cuts both ways: a wear report is evidence, and
  a number is better where a number is available.
- It is falsifiable. Zero disparity is `B1`; the wrong sign is a swapped eye;
  the wrong magnitude is a units error. **Three different failures, three
  different numbers.**

### Step 1 — the measurement that picks the architecture. No stereo code.

Run the game once with `GETV_MTXTRACE` (already present, `gfx_pc.c:2136`) and
record, for one gameplay frame:

- how many `G_MTX_PROJECTION` loads occur per frame, and
- whether the world pass is distinguishable from HUD/menu passes at that site.

**If the world's projection arrives at a single identifiable load per frame,
architecture B is cheap and A's double-tick risk is unnecessary. If it arrives
many times, or is indistinguishable from the HUD's, B's interception is
ambiguous and A becomes the honest choice.** This costs one launch and no code.

### Step 2 — the gate, written before the implementation

```
GETV_STEREO=1  GETV_STEREO_OFFSET=500

PREDICTION: computed from THAT BUILD's own printed frustum and the
            offset, in pixels per half-frame. Written in the log
            BEFORE the screenshot is taken.
REQUIRED:   |measured - predicted| <= 5 px, and the sign must match:
            the right eye's image further LEFT.
TODAY:      no stereo code exists. The gate cannot pass by accident.
```

**500 game units of separation is deliberately absurd** — `66` used the same
trick. A real per-eye response at that magnitude is unmissable, and a subtle
bug cannot hide inside it. The plausible 6-cm separation is tuned *after* the
mechanism is proven, never before: **a knob validated at one value is not a
setting** (`239`).

**What would a working build have to do differently to fail this?** It would
have to submit two views that differ by the requested offset and then render
them identically — which is `B1`, and is precisely what the gate exists to
catch. **A build that still renders one image cannot pass; a build with real
per-eye views cannot fail.** That is the test `70` demanded and `234` failed to
apply.

### Step 3 — only then, code

One behaviour change per run (`48`). The knob defaults **OFF** and stays
reachable as an off-switch (`DELETE NOTHING`). If `gfx_pc.c` is touched,
`tools/fetch-thirdparty.sh regen` is part of the same commit.

## 5. WHAT PHASE 1 IS NOT

Naming these now, because the recomp lost a day and a half to treating one
blocker as everything (`66`):

- **Not OpenXR.** No runtime, no session, no swapchain, no compositor. That is
  Phase 2 and it is a separate set of failures.
- **Not head tracking.** The offset in the gate is a constant. A pose is Phase 2.
- **Not hand aim.** `66` established aim and stereo are **independent** and can
  be worked in either order. Aim is not Phase 1.
- **Not the vignette, the HUD quad, or the desktop mirror.** `gevr_gl.c`'s other
  590 lines are comfort features for a build that already has stereo.
- **Not `gevr_xr.c`'s 1,383 lines.** They are Phase 2's reference, and §1 is the
  standing reason to read their call sites before trusting them.
