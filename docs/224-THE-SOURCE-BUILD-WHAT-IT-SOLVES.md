## §2 — 90 Hz AND GAME SPEED. THE ANSWER IS YES, AND RARE PROVED IT.

**`[READ]` `game/lv.c:105,335,345,348,979,983,985`:**

```c
f32 g_GlobalTimerDelta = 0;      /* lv.c:105 */
g_GlobalTimerDelta = 1.0f;       /* lv.c:335  NTSC, 60Hz            */
g_GlobalTimerDelta = 1.20000004768f;  /* lv.c:348  PAL, 50Hz       */
g_GlobalTimerDelta = g_JP_GlobalTimerDelta * 1.2f;  /* lv.c:983    */
```

**`[MEASURED]` `216` call sites consume `g_GlobalTimerDelta`.**

> **GOLDENEYE IS NOT FIXED-TICK. ITS LOGIC IS DELTA-SCALED THROUGH ONE GLOBAL —
> AND RARE ALREADY SHIPPED IT AT TWO DIFFERENT FRAME RATES BY CHANGING THAT ONE
> NUMBER.** The PAL build is a shipping, tested existence proof that the mechanism
> works. This is not a theory about what the code might tolerate.

**`[READ]` the consuming pattern is delta-correct, not counter-based:**

```c
[READ] bondview2.c:1375
  if ((sp30 < 30.0f) && ((sp30 + g_GlobalTimerDelta) >= 30.0f))
```

**That is threshold-crossing detection written to survive a variable delta** — it
fires once regardless of step size. **That idiom recurs throughout `bondview2.c`,
which is evidence the codebase was authored delta-aware rather than merely
tolerating it.**

### THEREFORE

| want | change |
|---|---|
| **90 Hz logic** | `g_GlobalTimerDelta = 60.0f/90.0f` (`0.6667f`) |
| **game speed control** | **multiply that same global.** Slow-mo, fast-mo, one term |
| **any headset rate** | `60.0f / actualHz`, computed per frame |

**`[INFERRED]` that all 216 consumers are delta-correct.**
**COUNTER-EXAMPLE SEARCH, as `182` requires:** `bondhead.c:284-285` **DIVIDES** by
the delta rather than multiplying —

```c
[READ] bondhead.c:284
  g_CurrentPlayer->bondheadmatrices[0].m[3][0] /= g_GlobalTimerDelta;
```

**— so at least one site treats it as a rate, not a step, and would behave
differently at 0.667 than at 1.2.** A counter-example EXISTS. **The claim is
therefore reduced: the MECHANISM is proven by PAL, but a 0.667 factor is a larger
excursion than Rare's 1.2 and individual sites must be worn, not assumed.**
**PAL's 1.2 is a 20% change; 90Hz is a 33% change in the other direction.**

## §4 — THE HONEST COSTS

1. **Toolchain** — Docker/WSL, plus asset extraction from the owner's ROM.
2. **Slower iteration** — full ROM build **then** recompile, versus today's patch
   rebuild. **This is the real price and it is paid on every change.**

   handling (N64 CIC checksum recalculation).
4. **Two places to look.** `vr.ps1`'s knobs and 223 documents assume the patch
   model. **Nothing is lost — patches keep working — but new work would live
   elsewhere.**

### THE RECOMMENDATION IS A SPLIT, NOT A MIGRATION
