## READ 9 — `autocrouchpos`: EVERY READER AND WRITER

**Complete, across `lib/ge/src`, `src`, `patches`.**

| | |
|---|---|
| **Writers of `autocrouchpos`** | `bondview.c:1406` and `player.c:175` (init to `CROUCH_STAND`), **`bondview2.c:2530` (reset to `CROUCH_STAND` every move tick)**, **`bondview2.c:2125` (set to `CROUCH_SQUAT` when the stan locus says the ceiling is low)** |
| **Writers of `crouchpos`** | `bondview.c:1545` (the player's own +/- input, clamped), `bondview2.c:5390` / `:5416` (tank enter/exit) |
| **The only reader of either** | **`currentPlayerGetCrouchPos`**, `bondview.c:1558` |

```c
/* bondview.c:1558 — and this one line is the whole answer */
s32 currentPlayerGetCrouchPos(void) {
    return (crouchpos < autocrouchpos) ? crouchpos : autocrouchpos;
}
```

**`CROUCH_SQUAT = 0`, `CROUCH_HALF = 1`, `CROUCH_STAND = 2`** (`bondconstants.h:1349`).
**So the function returns the MINIMUM — the more crouched of the two.**

> **`autocrouchpos` is a CAP, not a command.** It can only ever force you *more*
> crouched than you asked to be, never less, and it is re-raised to
> `CROUCH_STAND` at the top of every move tick before the stan test can lower
> it again (`:2530` then `:2125`). **It is stateless per frame.**
>
> **Read 9's stated question — "would it fight a written-in head height?" —
> answers NO, cleanly.** `autocrouchpos` and `crouchpos` feed
> `currentPlayerGetCrouchPos`, which feeds `ducking_height_offset` (`0`, `-60`,
> `FULL_CROUCH_OFFSET = -100`, `bondview2.c:6756-6768`). **`eyeheight` is a
> different field entirely**, composed alongside it at `bondview2.c:4566` and
> `:9152`. **Writing one does not touch the other.**

### BUT THE SEARCH FOUND THE THING THAT MATTERS MORE, AND IT COSTS H2

```c
/* chrprop.c:1411-1419 — inside the guard's shot resolution */
hitpart = HIT_CHEST;
if      (currentPlayerGetCrouchPos() == CROUCH_HALF)  hitpart = HIT_GENERAL;
else if (currentPlayerGetCrouchPos() == CROUCH_SQUAT) hitpart = HIT_GENERALHALF;
```

> **THE AI READS THE CROUCH STATE. IT DOES NOT READ `eyeheight`.**
>
> **`86` slice H2 gate G-H2-3 is *"physically crouch and a guard's shot passes
> overhead"*, and it is the gate that justifies option B over option A.**
> **Driving `eyeheight` from the VR head height does not pass it.** The guard
> would still aim at `HIT_CHEST`, because nothing told the crouch state
> anything.
>
> **So H2 option B is two writes, not one:**
>
> | Write | Buys |
> |---|---|
> | `eyeheight` (or `headpos.f[1]`, read 10) | the **view** follows your real head, inside the game's own composition — so the ceiling test at `bondview2.c:4418` sees it |
> | **`crouchpos`, from the physical crouch**, by PD's `/1.3` and `/1.6` divisors (`86` §3.4) | **the AI, cover, and hit resolution** — G-H2-3 |
>
> **`86` §3.4 already specified the second write** — *"two routes to the same
> three states, tested by `||` so neither has priority"* — **and this read names
> the GoldenEye field it lands in: `crouchpos`, via `bondview.c:1545`'s
> clamped adjust, or directly.** `86` costed H2 option B as *"a patch on the

> **And a bonus, unasked for:** because `currentPlayerGetCrouchPos` takes the
> **minimum**, a physical crouch written into `crouchpos` composes with the
> engine's own auto-crouch **for free and in the right direction**. Rule 8 —
> the two do not need synchronising, because the engine already resolves them.

### AND THERE ARE TWO INJECTION POINTS, WHICH `86` DID NOT KNOW

**`eyeheight` is not a root quantity. It is derived from `headpos.f[1]`** — the
engine's own animated head position, written by `bheadUpdatePos`
(`bondhead.c:95-97`) from a damped sum of the walk-bob matrices
(`bondhead.c:288-290`, scaled by `headamplitude` about `standheight`).

| Option | Where | Trade |
|---|---|---|
| **B-i: write `eyeheight`** | patch `bondviewUpdatePlayerCollisionPositionFields`, replace the `headpos.f[1] * …` term | **Overrides the walk-bob.** Which in VR is arguably correct — a bob the wearer's neck did not perform is a nausea source |
| **B-ii: write `headpos.f[1]`** | upstream, in the head path | **Composes with the bob** rather than replacing it, and needs no change to the eye-height line at all |

**Not chosen here. `48` rule 1 — this is a read, and B-i vs B-ii is a wearer
question of exactly the kind `86` H2 refused to settle by argument.**

> through the floor"* — is served by a clamp that is already there**, provided
> the write goes through this composition rather than around it. **That is the
> whole argument for option B in one line: our RT64 translation is downstream of
> this clamp, and a game-side write is upstream of it.**

## READ 11 — WHICH END IS THE MUZZLE. **ANSWERED, NO INSTRUMENT REQUIRED**

**`88` §5.1 established the axis and deliberately refused to assert the
direction. It is now established, from source, in three steps.**

**1. `guAlignF` maps local +Z to −dir.** `libultra/gu/align.c:44-56`:

```c
mf[2][0] = -x;   mf[2][1] = -y;   mf[2][2] = -z;    /* row 2 = -dir */
```

Row 2 is the image of the local **+Z** basis vector. **So local +Z → `-dir`.**

**2. `dir = gunofs − aimpoint`, so `-dir = aimpoint − gunofs` — the vector from
the gun TO the target.** The aim point comes from
`transformAndNormalizeByLength2Dto3D(&field_FFC, &coords, 1000.0f)`, whose
`z` component is `-norm` — **so the aim point sits at z ≈ −1000**, while
`83` measured the gun held at `(±11, −21, −33)`. **`dir.z ≈ +967`; `-dir.z ≈ −967`.**

**3. View space is −Z forward, confirmed twice independently:**

- **`hand->field_B64 = -flashmtx.m[3][2]`** (`gunfire.c:764`) — the muzzle
  flash's depth is stored as **negated z**, which is only a positive depth if
  forward is −z.
- **`83`'s measured gun position has z = −33** — in front of the eye.

> ### THEREFORE: **the model's barrel axis is local +Z, and `matrix_4x4_align`
> points it at the aim point.**
>
> There is no contradiction between "the model's barrel is +Z" and "view space
> is −Z forward". **They are different spaces**, and the align matrix is exactly
> the map between them: it takes model +Z to a view-space vector whose z is
> negative, i.e. forward. **`88` §5's mechanism holds, and the direction is now
> source-established rather than inferred from the stock game looking right.**

**Corroboration, from a second place in the same function:**
`matrix_column_3_scalar_multiply(flashext, flashmtx.m[0])` (`gunfire.c:754`)
extends the muzzle flash along **column 3 — the local Z axis — by
`MuzzleFlashExtension`.** The flash extends from the muzzle, away from the
shooter. **That is the same axis, used for the same purpose, by unrelated code.**

**AND THE FALSIFIER, WHICH COSTS ONE LOG LINE IN SLICE 0:**

> **`MuzzleFlashExtension` must be POSITIVE for every weapon.** If Slice 0
> prints a negative one, the barrel is local −Z and everything above is
> inverted. **The stats live in ROM data, not in C source**
> (`gitem_structs[item].item_weapon_stats`, `gun.c:712`), **so this cannot be
> read from the tree — it is the one part of read 11 that is genuinely an
> instrument, and it is one field on a line Slice 0 is printing anyway.**
>
> **Stated as a prediction before it is printed. `48` rule 2.**

## THE TRAP — CLOSED, AND THE ELEGANT SOLUTION IS NO CODE

**`88` §2 recorded that `get_ptr_item_statistics` returns a pointer into a
shared, mutable, per-item-type table, and that `copy_item_in_hand_to_main_list`
(`gun.c:734`) writes `PosX`/`PosY`/`PosZ` straight into it — so any "zero the
multipliers under VR" implementation would permanently mutate game data.**

**Three facts settle it, and none of them needs a fix:**

| | |
|---|---|
| **1. The writer is DEAD CODE** | **`copy_item_in_hand_to_main_list` has NO callers.** Nor does `copy_item_in_hand` (`gun.c:719`). Grepped across `lib/ge/src`, `src`, `patches`. **Nothing in the shipped game mutates the table at runtime** |
| **2. Our own code only READS** | `ge_vr_bindtest.c:885-887` reads `->PosX` through a two-field shim and writes nothing. **The seam patch is not exposed** |
| **3. THE MUTATION IS NO LONGER WANTED** | **`88` §5's whole point is that `PlayX/Y/Z` should NOT be suppressed.** The coupling is the mechanism A1 wanted. **The code that would have sprung the trap is code we have now decided not to write** |

> ### THE ELEGANT SOLUTION IS TO WRITE NOTHING, AND THE PROJECT HAS A DOC ABOUT WHY
>
> **A guard here would be `42` exactly.** `48` rule 7: *"know who destroys what
> you build, and when"* — and `42`'s finding was **"every safeguard lived in a
> hook that was never reached."** **Adding a const wrapper, an accessor, or a
> VR-time restore for a table whose only writer is dead, to protect against a
> mutation we have decided not to perform, is a safeguard on a path nothing
> reaches.** It would cost a patch name, a long build, and a future session's
> confusion about why it exists.
>
> **What it gets instead is one line in the rules, which costs nothing and
> cannot rot:**
>
> **► NEVER WRITE THROUGH `get_ptr_item_statistics`. It returns a pointer into
> shared per-item ROM-loaded data, not a copy, and the only stock writer is dead
> code. A write there is permanent, global to the weapon type, and invisible.**
>
> **Recorded in `00`'s rules rather than enforced in code.** Rule 10's sibling:
> **a hazard that is documented and never triggered costs nothing; a guard that
> is built and never reached costs a name, a build, and a puzzle.**

**One caveat kept honest:** *"no callers"* is a grep of this tree. **These are
recompiled functions and the recomp can reach a symbol the C never names.** If
a future session sees `PosX` drift, this is the first place to look — **and it
is now written down, which is the whole point.**
